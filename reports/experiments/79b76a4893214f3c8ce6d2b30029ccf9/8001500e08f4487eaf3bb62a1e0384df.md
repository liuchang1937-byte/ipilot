1. 如何阻止助手循环调用工具？
阻止助手循环调用工具的关键，是识别“重复且无进展”并设置治理边界，而不是简单禁止重复调用。

首先，要明确目标与完成/终止条件，避免目标或终止条件含糊；同时让模型能看到历史动作，避免因看不到已执行动作而重复调用；错误重试要有退避，避免无效重试形成循环；还要避免两个策略互相推翻[1]。

检测上，可以对“状态—动作—参数”生成轨迹指纹，检测短周期重复和无进展步数；也可以为工具名与规范化参数建立动作指纹，并比较新增证据、待办是否减少和状态是否变化。需要注意，重复工具调用本身不等于死循环，例如分页检索和受控重试可能是合理的；重复但没有进展才应触发治理[1]。

治理上，应设置最大调用次数、时间和费用预算；触发阈值后熔断或转人工；明确完成条件、压缩重复历史、增加失败分类与替代路径；发现空转后先判断错误类型，再修正参数、换工具或重新规划；多 Agent 系统还要检查交接图中的环；预算耗尽时返回已完成工作和具体卡点[1]。

在工具调用失败时，执行前用 Schema 校验并对可修复格式做受控纠正，缺少业务参数时向用户澄清；调用时设置超时、取消、幂等键和分类重试，失败后把结构化错误返回模型选择替代工具或降级；对部分成功的外部操作使用补偿事务；超过预算后停止并转人工，所有动作记录审计与 Trace。还要区分明确失败和结果未知：例如请求超时后订单可能已经创建，此时优先用请求 ID 查询状态，再决定是否重试。权限拒绝和业务参数错误通常不能原样重试，临时限流则可尊重 Retry-After 并做退避[3]。

此外，可以通过工具路由降低选错工具的概率：先按领域和权限建立工具目录，运行时先做规则或语义检索得到小候选集，再让模型选择；可使用分层路由、工具组、历史成功率和上下文约束，并对高风险工具二次确认。模型判断现有工具不合适时可以扩大候选范围，而不是被错误路由永久锁住[2]。

2. 如何识别助手没有执行却宣称完成的情况？
识别“没有执行却宣称完成”的关键，是不把模型自然语言自述当作完成依据，而把它视为“任务幻觉”：模型把准备做、模拟做或生成了调用文本误报为真实完成[4]。完成状态应由执行器根据工具成功响应、外部资源状态或可验证产物判定，而不是由模型自己决定[4]。系统应区分 planned、running、succeeded、failed，并要求每个完成声明关联工具调用 ID 和结果证据[4]。核验时，关键操作完成后要再次读取外部状态确认；失败时应明确报告，而不是补写成功叙述[4]。例如，模型生成了发送通知的计划，不能据此声称通知已发送；接口只返回“已受理”也不代表业务最终成功[4]。调用超时时应优先查询请求结果，而不是盲目重试[4]。在恢复或中断场景中，检查点应保存未决工具请求、产物版本与已确认的外部操作，恢复时先核查这些操作的真实结果，尤其不能因为没有收到响应就再次付款或发送通知[5]。还可以通过轨迹指纹、无进展步数、新增证据、待办减少和状态变化来检测空转或无实际执行，并明确完成条件[1]。评测也应专门覆盖响应丢失、部分成功、异步处理和伪造成功内容，统计错误完成声明率，而不是只给流畅的最终回复打高分[4]。因此，识别流程可概括为：提取完成声明，查找对应工具调用 ID 与回执，核验外部资源状态或可验证产物，检查状态机是否真正进入成功或已验证状态；缺少工具证据、外部状态未确认或仅处于计划/执行中/结果未知时，就应判定为未完成或未验证，而不是已完成[4][5][1]。
