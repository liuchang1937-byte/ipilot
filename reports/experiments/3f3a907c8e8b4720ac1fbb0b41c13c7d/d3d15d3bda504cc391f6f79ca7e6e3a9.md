1. 怎样阻止助手循环调用工具？
要阻止助手循环调用工具，核心不是简单禁止所有重复调用，而是识别“无进展的重复”并加以治理。资料指出，重复工具调用本身不等于死循环，分页检索和受控重试可能是合理的；重复但没有进展才应触发治理[1]。

可按以下流程做：

1. 明确目标和终止条件：目标或终止条件含糊、工具结果没有改变状态、模型看不到历史动作、错误重试没有退避，或两个策略互相推翻，都会导致路径震荡、重复调用和死循环[1]。因此先要明确完成条件。

2. 检测重复和无进展：对“状态—动作—参数”生成轨迹指纹，检测短周期重复和无进展步数；也可为工具名与规范化参数建立动作指纹，同时比较新增证据、待办减少和状态变化[1]。如果只是重复调用，但没有新增证据、待办没有减少、状态没有变化，就应触发治理。

3. 设置预算和熔断：设置最大调用次数、时间和费用预算；触发阈值后熔断或转人工[1]。预算耗尽时，返回已完成工作和具体卡点，让用户知道系统为何停止[1]。

4. 做恢复与替代路径：治理上要明确完成条件、压缩重复历史、增加失败分类与替代路径；发现空转后，先判断错误类型，再修正参数、换工具或重新规划；多 Agent 系统还要检查交接图中的环[1]。

5. 减少选错工具和错误路由：工具很多时，先按领域和权限建立工具目录，为工具生成简洁、可区分的能力描述；运行时先做规则或语义检索得到小候选集，再让模型选择；可使用分层路由、工具组、历史成功率和上下文约束，并对高风险工具二次确认[2]。模型判断现有工具不合适时可以扩大候选范围，而不是被错误路由永久锁住[2]。这有助于减少因误选工具而反复失败。

6. 在工程上保留循环控制权：当流程较小但对状态、延迟、权限、日志或故障恢复有强定制要求时，自行实现循环往往更透明，能精确记录状态、限制权限并支持断点恢复[3]。手写并不意味着重造所有组件，可以复用模型客户端、追踪和存储等成熟基础设施，只掌握关键控制逻辑[3]。

简单说：先定义完成条件，再检测“重复且无进展”，配合轨迹/动作指纹、调用预算、熔断、替代路径和工具路由优化；触发阈值后停止或转人工，并把已完成工作和卡点返回给用户[1][2][3]。

2. 如何识别助手没有执行却宣称完成的情况？
识别“没有执行却宣称完成”的核心，是把自然语言完成声明与真实执行事实分开核验。资料指出，这属于“任务幻觉”：模型把“准备做、模拟做或生成了调用文本”误报为真实完成；完成状态不能由模型自述决定，而应由执行器根据工具成功响应、外部资源状态或可验证产物判定[4]。

具体可从以下方面识别：
1. 检查完成声明是否关联工具调用 ID 和结果证据。系统应区分 planned、running、succeeded、failed，并要求每个完成声明关联工具调用 ID 和结果证据[4]。
2. 检查是否只有计划或调用文本。模型生成了发送通知的计划，不能据此声称通知已发送；接口只返回已受理，也不代表业务最终成功[4]。
3. 核验外部状态。关键操作完成后应再次读取外部状态确认；失败时应明确报告，而不是补写成功叙述[4]。
4. 区分多种状态。应区分计划、执行中、成功、已验证和结果未知，完成声明只能依据工具回执与外部状态核验[4]。
5. 结合结构化计划与验收条件。规划结果应是可执行的任务结构，由执行器校验步骤、依赖和完成条件；一个任务是否完成要由验收条件判断，不能仅因模型写出了看似完整的步骤就视为规划成功[5]。
6. 检查运行时控制与记录。运行时控制器负责停止条件、异常处理和检查点，避免模型输出了计划却没有执行；记忆不能只保存聊天文本，还要保存已完成步骤、待办和工具回执[6]。

可操作的识别流程是：先看助手是否声称完成；再查是否存在对应工具调用 ID、工具成功回执、外部资源状态或可验证产物；如果只有计划、模拟调用文本、已受理回执或口头叙述，就应判定为未完成或结果未知，而不是完成[4]。例如，助手说“通知已发送”，但只有发送计划或接口仅返回已受理，不能认定为业务最终成功[4]。调用超时时，也应优先查询请求结果，而不是盲目重试[4]。

1. 怎样阻止助手循环调用工具？
阻止助手循环调用工具，核心是把“是否该继续行动”变成可检测、可预算、可熔断的控制问题，而不是只靠提示模型不要重复。[1]

可按以下流程处理：

1. 先消除常见诱因：明确目标和终止/完成条件；确保工具结果会改变状态；让模型能看到历史动作；错误重试要有退避；避免两个策略互相推翻。[1] Agent 本身应在完成目标或触发停止条件时停止，自主性也应受权限、预算和验收条件约束。[3]

2. 建立指纹与进展检测：对“状态—动作—参数”生成轨迹指纹，检测短周期重复和无进展步数；也可为工具名与规范化参数建立动作指纹。同时比较新增证据、待办是否减少、状态是否变化。注意，重复工具调用不等于死循环，分页检索和受控重试可能合理；重复但没有进展才应触发治理。[1]

3. 设置预算和熔断：设置最大调用次数、时间和费用预算；达到阈值后熔断或转人工。预算耗尽时返回已完成工作和具体卡点，让用户知道系统为何停止。[1]

5. 若循环来自选错工具，可先用工具目录和路由缩小候选：按领域和权限建目录，生成简洁可区分的能力描述，运行时用规则或语义检索得到小候选集，再让模型选择；可结合分层路由、工具组、历史成功率和上下文约束，高风险工具二次确认。评测关注工具 Recall、误选率、参数正确率、Token 和延迟等。[2]

具体识别流程可以包括：
1. 区分执行状态：系统应区分 planned、running、succeeded、failed，或区分计划、执行中、成功、已验证和结果未知；完成声明只能依据工具回执与外部状态核验[4]。
