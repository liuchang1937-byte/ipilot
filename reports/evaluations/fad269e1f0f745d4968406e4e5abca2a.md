1. Function Calling 是什么？
Function Calling 是模型根据用户意图和工具 Schema 生成结构化调用请求的能力 [1]。模型只负责选择工具并给出参数，宿主程序负责校验、鉴权、真实执行，再把结果返回模型生成最终回答 [1]。它不是模型直接执行函数，也不能替代超时、重试、幂等和安全控制 [1]。例如，用户要查询订单物流，开发者提供查询工具的名称、描述与参数约束，模型输出工具名和订单号，服务端校验身份并查询，最后把物流结果作为工具消息回传 [1]。模型可能直接回答，也可能连续调用多个工具，所以不一定固定两次模型请求；工具结果要关联到对应调用，JSON 格式正确也不代表订单号、权限或业务条件正确，执行前仍需确定性检查，不能直接运行模型生成的任意代码 [1]。与 MCP 相比，Function Calling 是模型表达“调用哪个工具及参数”的交互能力，MCP 是宿主连接外部工具和资源的标准协议，二者处于不同层次；应用可以把 MCP 发现的工具转换成模型可理解的工具 Schema，再由 Function Calling 选择 [2]。工具少、只在单个应用内部使用时，直接 Function Calling 加本地函数注册最简单；需要跨应用复用、独立部署、动态发现或第三方维护时，可考虑 MCP，但两者并非互斥 [3]。

2. 在 Function Calling 中，模型和宿主分别做什么？
在 Function Calling 中，模型负责表达“调用意图”：它根据用户意图和工具 Schema，选择要调用的工具并生成结构化调用请求及参数，例如输出工具名和订单号；模型不直接执行函数。[1] 模型也可能直接回答，还可能连续调用多个工具，因此流程不一定固定为两次模型请求。[1]

宿主/宿主程序负责把模型的调用意图真正落地：提供或转换工具 Schema，校验参数、身份与权限，进行鉴权，真实执行工具，或通过协议请求外部服务执行，并把执行结果关联到对应调用后回填给模型，让模型生成最终回答。[1][2][4] 例如查询订单物流时，开发者提供查询工具的名称、描述与参数约束，模型输出工具名和订单号，服务端校验身份并查询，最后把物流结果作为工具消息回传。[1]

需要注意，执行前仍需确定性检查，因为 JSON 格式正确不代表订单号、权限或业务条件正确；不能直接运行模型生成的任意代码，也不能用 Function Calling 替代超时、重试、幂等和安全控制。[1] 在 MCP 等组合链路中，Host 可将模型选择转成真实协议请求：Client 从 Server 发现工具，Host 将描述转换成模型工具定义，模型生成调用意图，Host 校验后通过 Client 发请求，Server 执行并返回结果，Host 再向模型反馈。[2][4]
