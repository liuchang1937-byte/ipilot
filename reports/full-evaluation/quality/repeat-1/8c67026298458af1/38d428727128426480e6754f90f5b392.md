1. SSE 与 WebSocket 分别适合什么通信场景？
SSE 基于 HTTP 长连接，主要由服务端向客户端单向推送文本事件，浏览器支持自动重连，适合 LLM Token 流等场景 [1]。例如文本生成可以用一次 HTTP 请求发送问题，再用 SSE 接收增量内容；用户取消可以另发请求，不必为所有对话引入 WebSocket [1]。SSE 不适合高频双向通信和二进制媒体 [1]。

WebSocket 升级为全双工连接，可双向低延迟传输文本或二进制，适合实时协作，以及双方持续发送事件的场景 [1]。但它需要自己处理心跳、重连、代理兼容和水平扩展；可靠重连和消息去重仍由应用实现 [1]。无论哪种方式，代理缓冲、心跳和慢消费者都会影响实际延迟 [1]。SSE 的浏览器连接限制与 HTTP 版本有关，不能把 HTTP/1.1 的常见限制当作所有部署都相同 [1]。

2. 在实时语音通信场景中，相比 SSE 与 WebSocket，为什么还会考虑使用 WebRTC？
在实时语音通信中，SSE 和 WebSocket 虽然能建立长连接，但它们在媒体传输能力上有局限，因此 WebRTC 仍会被考虑。SSE 基于 HTTP 长连接，主要是服务端到客户端的单向文本事件推送，适合 LLM Token 流，但不适合高频双向和二进制媒体[1]。WebSocket 是全双工连接，可双向低延迟传文本或二进制，适合实时协作，但它本质上只是可靠的双向字节通道，像媒体编解码、抖动缓冲、拥塞控制、NAT 穿透等媒体能力需要自行实现[1][2]。实时语音场景不仅要传控制消息，还要传双向音频流，并处理同时说话/打断、网络抖动和丢包；如果使用常基于 TCP 的 WebSocket，丢包可能带来队头阻塞，等待旧包重传会拖累实时媒体体验[2]。WebRTC 是为实时音视频设计的，内建媒体编解码、抖动缓冲、拥塞控制、NAT 穿透和低延迟传输，因此更适合承载音频和数据通道；典型做法是用 WebRTC 承载音频和数据通道，用 WebSocket 传控制事件也可以，选择取决于延迟、媒体质量和部署复杂度[2]。不过 WebRTC 并非绝对只走 UDP，也不是永远不重传，实际会受网络和中继影响；选择时应比较通话质量、端到端延迟、穿透和运维，不应承诺固定毫秒数[2]。
