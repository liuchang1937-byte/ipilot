1. SSE 与 WebSocket 分别适合什么通信场景？
SSE 与 WebSocket 的适用场景可按通信方向、数据类型和重连/运维需求区分。SSE 基于 HTTP 长连接，主要由服务端向客户端单向推送文本事件，浏览器支持自动重连，因此适合服务端持续产生增量、客户端只需接收的场景，典型是 LLM Token 流：客户端用一次 HTTP 请求发送问题，再用 SSE 接收增量内容；用户取消可另发请求，不必为所有对话引入 WebSocket[1]。SSE 不适合高频双向通信和二进制媒体[1]。在类似远程服务的传输中，也可以在 HTTP 请求传递消息后通过 SSE 推送多个事件，并非所有响应都必须保持一个长连接[3]。WebSocket 升级为全双工连接，可双向低延迟传输文本或二进制，适合双方持续发送事件的场景，例如实时协作[1]。它也可用于传控制事件，但 WebSocket 本身只是可靠的双向字节通道，媒体能力需自行实现；实时语音 Agent 通常用 WebRTC 承载音频和数据通道，用 WebSocket 传控制事件也可以[2]。使用 WebSocket 时，心跳、重连、代理兼容和水平扩展需要自己处理，可靠重连和消息去重仍由应用实现[1]；它常基于 TCP，丢包可能造成队头阻塞[2]。此外，代理缓冲、心跳和慢消费者都会影响实际延迟[1]。

2. 在实时语音通信场景中，相比 SSE 与 WebSocket，为什么还会考虑使用 WebRTC？
在实时语音通信中，SSE 基于 HTTP 长连接，主要由服务端向客户端单向推送文本事件，适合 LLM Token 流，但不适合高频双向和二进制媒体[1]。WebSocket 虽然升级为全双工，可双向低延迟传输文本或二进制，适合实时协作，但它本质上只是可靠的双向字节通道，需要应用自己处理心跳、重连、代理兼容和水平扩展[1]；而且 WebSocket 常基于 TCP，丢包可能造成队头阻塞，对实时音频不利[2]。WebRTC 则是针对实时音视频设计的，包含媒体编解码、抖动缓冲、拥塞控制、NAT 穿透和低延迟传输[2]。因此在实时语音 Agent 中，通常用 WebRTC 承载音频和数据通道，用 WebSocket 传控制事件也可以，具体选择取决于延迟、媒体质量和部署复杂度[2]。例如用户语音输入与模型语音输出同时进行，还要支持打断和网络抖动时，媒体通道更需要实时性，而不是等待每个旧包重新到达[2]。不过 WebRTC 并不是绝对只走 UDP，也不是永远不重传，实际会受网络与中继影响；选择时应比较通话质量、端到端延迟、穿透和运维，不应承诺固定毫秒数[2]。
