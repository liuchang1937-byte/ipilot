1. 在服务器持续推送文本方面，SSE 与 WebSocket 的差异是什么？
资料显示，SSE 基于 HTTP 长连接，主要由服务端向客户端单向推送文本事件，浏览器支持自动重连，适合 LLM Token 流；因此在“服务器持续推送文本”场景，SSE 是天然的单向文本流通道。WebSocket 则升级为全双工连接，可双向低延迟传输文本或二进制，适合实时协作。若只需要服务器持续推送文本，SSE 不必引入双向 WebSocket；例如文本生成可用一次 HTTP 请求发送问题，再用 SSE 接收增量内容，用户取消可另发请求。WebSocket 更适合双方持续发送事件，但可靠重连和消息去重仍由应用实现，同时需自己处理心跳、重连、代理兼容和水平扩展；SSE 不适合高频双向和二进制媒体。两者实际延迟都会受代理缓冲、心跳和慢消费者影响。SSE 的浏览器连接限制与 HTTP 版本有关，不能把 HTTP/1.1 的常见限制当作所有部署都相同。[1]

2. 在双向交互方面，SSE 与 WebSocket 的差异是什么？
在双向交互方面，核心差异是：SSE 基于 HTTP 长连接，主要由服务端向客户端单向推送文本事件，属于单向服务端推送；客户端若要向服务端发送消息，通常需要另发 HTTP 请求。WebSocket 则升级为全双工连接，双方可以持续、低延迟地互发文本或二进制消息，因此更适合需要双向实时交互的场景。[1]

具体来说，SSE 适合 LLM Token 流这类服务端增量输出场景，浏览器还支持自动重连；但它不适合高频双向通信和二进制媒体。WebSocket 适合实时协作或双方持续发送事件，但需要自己处理心跳、重连、代理兼容和水平扩展，可靠重连与消息去重也仍由应用实现。[1]

例如，文本生成可以用一次 HTTP 请求发送问题，再用 SSE 接收增量内容；用户取消可以另发请求，不必为所有对话引入 WebSocket。[1]

此外，SSE 的浏览器连接限制与 HTTP 版本有关，不能把 HTTP/1.1 的常见限制当作所有部署都相同；无论哪种方式，代理缓冲、心跳和慢消费者都会影响实际延迟。[1]
