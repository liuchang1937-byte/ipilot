1. 文字送入模型前如何转换为 token？
文字送入模型前，先由对应模型的 tokenizer 处理：它把输入字符串按既定规则切分成 token，再把每个 token 映射为有限词表中的 Token ID；模型本身只处理这些 ID，而不是直接处理原始文字。[1] 常见做法包括 BPE、WordPiece 或 Unigram，它们从字符/字节出发学习高频子词组合，并保留特殊 Token。[1] 因此，Token 不等同于汉字、单词或字符，一个词可能被拆成多个子词，字节级方案也能表示少见字符串。[1] 推理时按既定规则编码；模型输出 ID 后，再通过解码把 Token 序列还原为文本。[1] 词表和算法会影响多语言压缩率、代码表示、未知字符、上下文占用与计费；词表学习是在压缩效率、覆盖范围和序列长度之间折中。[1] 领域术语若被拆得过碎，会增加长度与费用，代码和多语言尤其需要评估；估算上下文时应使用对应模型的 tokenizer，不能默认所有模型共用固定的字数换算比例。[1]

2. 分词方式为何影响 token 长度与模型使用成本？
分词方式决定同一段文本会被切分成多少个 Token：Tokenizer 先把字符串转换为有限词表中的 Token ID，模型只处理这些 ID [1]。常见 BPE、WordPiece 或 Unigram 从字符/字节出发学习高频子词组合，因此不同词表和算法对同一文本的切分结果不同，Token 也就不等同于汉字、单词或字符，一个词可能被拆成多个子词 [1]。如果某种分词方式把文本切得更碎，Token 数量就会变多，从而增加上下文占用和模型使用成本；资料明确指出词表和算法会影响多语言压缩率、代码表示、未知字符、上下文占用与计费，领域术语拆得过碎会增加长度与费用 [1]。反过来，压缩率更高、覆盖更合适的分词方式可以用更少 Token 表示相同文本，减少长度和费用。因此估算上下文或成本时应使用对应模型的 tokenizer，不能默认所有模型共用固定的字数换算比例 [1]。
