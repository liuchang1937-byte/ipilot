该循环可概括为 Thought—Action—Observation 循环：模型先推理并决定工具及参数，宿主执行后把观察结果送回模型，直到满足结束条件[1]。具体步骤与状态流转是：1）用户目标进入规划模块，规划结果与已有状态组成模型上下文[3]；2）调用模型推理/决策，模型选择工具并给出参数，或产出最终答案[1][3]；3）判断模型返回是最终答案还是工具请求[1]；4）若是最终答案，则结束循环[1]；5）若是工具请求，检查工具名、参数和权限，由执行器校验参数并运行，工具执行由宿主完成[1][3]；6）执行结果作为 Observation 写回状态和记忆，并追加工具结果进入下一轮；工具报错应作为明确观察反馈，不能直接吞掉[1][3]；7）带着更新后的观察/状态进入下一轮，模型再判断是否继续，直到满足结束条件[1]。状态流转上，应显式保存当前阶段、目标、计划、已完成步骤、工具结果、约束和预算；每个状态转移写入事件日志并定期生成 Checkpoint，恢复时从最近检查点重放未完成事件[2]。运行时控制器负责停止条件、异常处理和检查点，工程上还要限制步数、预算和重复调用，避免无限循环[1][3]。

2. 实现助手推理与工具调用交替循环需要哪些核心组件，例如推理引擎、工具调用协议、状态管理和结果回传机制？
实现助手推理与工具调用交替循环，通常需要以下几类核心组件协同工作：

1. 推理/决策引擎与规划模块：LLM负责理解任务与决策，规划模块把复杂目标拆成可执行步骤[3]。ReAct类循环中，模型先形成Thought并决定Action，即选择工具及参数[1]。

2. 工具层与工具调用协议：工具负责搜索、执行代码或调用API，使Agent作用于外部环境[3]。调用时由宿主检查工具名、参数和权限，然后执行[1]。契约上应定义输入输出、权限、超时和幂等约束；复杂协作可用结构化调用、消息传递或共享状态[4]。

3. 状态/记忆管理：记忆保存对话和任务状态，不能只保存聊天文本，还要保存已完成步骤、待办和工具回执[3]。规划结果与已有状态组成模型上下文[3]。共享状态应通过受控更新接口提交，避免多个Agent随意覆盖同一任务记录[4]。

4. 结果回传与观察反馈：宿主执行工具后，把观察结果送回模型，形成Thought—Action—Observation循环，直到满足结束条件[1]。工具报错也应作为明确观察反馈，不能直接吞掉[1]。结果写回状态和记忆，模型再判断是否继续[3]。

5. 运行时控制器与停止/容错机制：运行时控制器负责停止条件、异常处理和检查点，避免模型输出了计划却没有执行[3]。工程实现还要限制步数、预算和重复调用[1]。

3. 助手如何根据当前推理决定调用哪个工具、传递什么参数以及何时进入工具调用？
助手决定工具调用时，核心是“模型基于当前目标、上下文和工具 Schema 生成结构化调用请求，宿主再校验执行”。具体来说：模型会依据用户意图和工具 Schema 判断是否需要外部能力，并选择工具、生成参数；它可能直接回答，也可能连续调用多个工具，因此不固定为两次模型请求 [5]。在 Agent 场景中，它会依据目标和运行时反馈动态决定下一步做什么、调用哪个工具以及何时结束 [6]。当工具很多时，应先按领域和权限建立工具目录，为工具生成简洁、可区分的能力描述；运行时先做规则或语义检索得到小候选集，再让模型在少量相关 Schema 中选择，并可使用分层路由、工具组、历史成功率和上下文约束来减少 Token、避免选错；如果模型判断现有工具不合适，可以扩大候选范围，而不是被错误路由永久锁住 [7]。工具描述应包含何时使用、何时不用和参数语义，相似工具要有明确区分 [7]。参数方面，模型负责根据工具 Schema 生成工具名和参数，但宿主程序负责校验、鉴权、真实执行，再把结果返回模型生成最终回答；JSON 格式正确也不代表订单号、权限或业务条件正确，执行前仍需确定性检查 [5]。对于高风险工具应二次确认，权限过滤在执行时再次校验 [7]。因此，“何时进入工具调用”取决于当前推理是否判断需要外部能力且存在合适工具；“调用哪个工具”由意图、描述、候选路由和上下文约束共同决定；“传什么参数”由模型按 Schema 生成，但必须经过宿主侧确定性校验与授权后才真正执行 [5][6][7]。

4. 工具执行结果如何返回给助手，并让助手基于工具结果继续推理？
工具执行结果不是由模型自己直接运行工具后“内部知道”，而是由宿主/应用作为执行器解析并执行模型提出的工具请求，再把结果作为新的观察反馈给助手，使助手进入下一轮推理。[1][8]

具体流程可以概括为：在 ReAct 模式中，循环是 Thought—Action—Observation：模型决定要用的工具及参数，宿主执行后把观察结果送回模型，直到满足结束条件。[1] 工程实现上通常是一个有界循环：构建消息、调用模型、判断返回的是最终答案还是工具请求；若是工具请求，就检查工具名、参数和权限，执行后追加工具结果，再进入下一轮。[1] 在 Agent 数据流中，规划结果与已有状态组成模型上下文，模型选择工具，执行器校验参数并运行，结果写回状态和记忆，模型再判断是否继续。[3]

从模型训练与推理角度看，工具 Schema 会与上下文一起输入，模型预测工具名和参数 Token，宿主解析并执行；训练样本也包含“工具结果—最终回答”这样的模式，因此模型需要学会解释工具结果并据此生成最终回答。[8] 结果返回后，助手会基于新的观察继续推理或决策，可能需要多次工具调用，直到得到最终答案或触发停止条件。[1][3]

需要注意：工具报错应作为明确观察反馈，不能直接吞掉；运行时控制器负责停止条件、异常处理和检查点，也应限制步数、预算和重复调用。[1][3] 记忆不只保存聊天文本，还要保存已完成步骤、待办和工具回执，以支持后续判断。[3] 例如查询订单时，如果缺少订单号，模型应先询问用户，而不是猜一个值；拿到工具返回结果后，再解释结果并形成最终回答。[8]
