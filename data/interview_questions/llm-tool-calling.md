# LLM 工具调用面试题

> 题目参考[小林面试笔记](https://xiaolinnote.com/ai/)；答案以自己的表述整理并补充原理、例子和工程边界。
> 参考答案用于理解与复盘，评分应关注核心概念与逻辑，不要求逐字背诵或覆盖所有扩展细节。

## T001｜什么是 Function Calling？原理是什么？

- 知识点：Function Calling
- 难度：基础
- 参考答案：Function Calling是模型根据用户意图和工具Schema生成结构化调用请求的能力。模型只负责选择工具并给出参数，宿主程序负责校验、鉴权、真实执行，再把结果返回模型生成最终回答。它不是模型直接执行函数，也不能替代超时、重试、幂等和安全控制。例如，用户要查询订单物流，开发者提供查询工具的名称、描述与参数约束，模型输出工具名和订单号，服务端校验身份并查询，最后把物流结果作为工具消息回传。模型可能直接回答，也可能连续调用多个工具，所以不一定固定两次模型请求。工具结果要关联到对应调用，JSON 格式正确也不代表订单号、权限或业务条件正确；执行前仍需确定性检查，不能直接运行模型生成的任意代码。
- 评分要点：说明 Schema、模型选择与参数生成、宿主校验执行、结果回填；不把模型生成调用请求等同于执行。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/1_function_calling.html)

## T002｜LLM 是如何学会调用外部工具的？

- 知识点：Function Calling
- 难度：中等
- 参考答案：模型通过预训练获得语言与代码模式，再在指令微调或偏好训练中学习“用户请求—工具描述—结构化调用—工具结果—最终回答”的样本。推理时工具Schema与上下文一起输入，模型预测工具名和参数Token；宿主解析执行。提示和约束解码可提高格式稳定性，但最终仍需程序校验。示范数据让模型学会的不只是 JSON 语法，还包括调用时机、工具选择、参数映射和结果解释。比如查询订单需要先取得订单号，缺失时应询问用户，而不是猜一个值。偏好或奖励训练可以改善不必要调用和失败恢复，但并非每个模型都必须经过同一种训练流程。Schema 描述有助于推理时泛化到新工具，却不会凭空授予网络权限；最终动作仍由应用执行和记录。
- 评分要点：训练样本、Schema条件生成、宿主执行和校验。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/2_llm_tool_learning.html)

## T003｜大模型的 Function Call 能力是怎么训练出来的？

- 知识点：Function Calling
- 前置知识：Function Calling
- 难度：进阶
- 参考答案：数据应覆盖正确调用、不应调用、缺参数先澄清、多工具选择、连续调用、并行调用及失败恢复。通过SFT学习调用格式和决策，再可用偏好优化提升工具选择与参数质量。训练还要加入未知工具、恶意描述和异常结果，避免模型只会理想路径；评测分别检查选工具、参数、执行后回答和拒绝调用。一条训练样本可包含用户需求、候选工具定义、正确调用请求、执行观察和最终答复。需要构造相似工具的困难负例，以及参数缺失、过期结果、权限拒绝等情况，防止模型只记住名称。奖励不能只检查调用格式，执行结果与任务是否完成也很重要。测试时把训练出现过的工具和新工具分开，分别测工具选择、参数有效性、多轮完成率和不该调用时的拒绝率，避免数据泄漏掩盖问题。
- 评分要点：数据构造、训练阶段和分层评测。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/3_fc_training.html)

## T004｜什么是 MCP（模型上下文协议）？讲讲它的核心内容？

- 知识点：MCP
- 难度：基础
- 参考答案：MCP是连接AI宿主与外部能力的标准协议，统一能力发现、工具调用、资源读取和提示模板等交互。它解决不同应用重复编写集成的问题，使MCP Server可以被多个Host复用。MCP不替模型决定业务策略，也不会自动解决权限、可信度和工具副作用，这些仍由宿主和服务端治理。典型能力包括 Tools、Resources 和 Prompts：工具提供可调用操作，资源提供上下文数据，提示模板提供可复用消息构造。工具既可能只读，也可能产生副作用，不能把 Tools 一律定义为写操作。应用与服务端按协议协商能力并交换消息，模型并不直接解析网络协议。标准化降低重复集成成本，但真实可用性仍取决于双方支持的协议版本、身份验证和工具质量。
- 评分要点：说明标准化接入与能力协商；区分 Tools、Resources、Prompts；知道工具可只读也可有副作用。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html)

## T005｜MCP 由哪几部分组成？

- 知识点：MCP
- 前置知识：MCP
- 难度：中等
- 参考答案：典型结构包括Host、Client和Server。Host承载用户体验与模型，Client在Host内维护到某个Server的协议会话，Server暴露Tools、Resources和Prompts等能力；底层通过支持的传输交换JSON-RPC消息。完整实现还包括初始化和能力协商、生命周期、错误处理及权限策略。例如，一个桌面 AI 应用是 Host，内部为文件服务与数据库服务各建立 Client 连接，两个 Server 分别暴露自己的工具和资源。初始化时协商协议版本与能力，之后发现工具、发送请求并关联响应，结束时释放连接。Host 决定哪些能力对模型可见，Server 仍应独立检查访问权限。三种角色描述的是职责，不要求部署成三个独立进程，也不是模型、浏览器和数据库的固定对应关系。
- 评分要点：三类参与方、暴露能力、协议交互和生命周期。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/5_mcp_components.html)

## T006｜MCP 和 Function Calling 有什么区别？有没有实际跑过 MCP？

- 知识点：工具协议选型
- 前置知识：Function Calling、MCP
- 难度：中等
- 参考答案：Function Calling是模型表达“调用哪个工具及参数”的交互能力；MCP是宿主连接外部工具和资源的标准协议，二者处于不同层次。应用可以把MCP发现的工具转换成模型可理解的工具Schema，再由Function Calling选择。实践回答应说明使用的Host/Server、传输方式、一次调用链路和遇到的权限或调试问题。完整链路可以是：Client 从 Server 发现工具，Host 将描述转换成模型工具定义，模型生成调用意图，Host 校验后通过 Client 发请求，Server 执行并返回结果，Host 再向模型反馈。Function Calling 可以调用普通本地函数，MCP 也可被确定性的应用直接调用，所以协议本身并不依赖某个模型 API。回答实践时应说明实际做过的部分，不能把配置成功误认为权限与异常处理已经完善。
- 评分要点：层次区分、组合关系和真实实践细节。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/6_mcp_vs_fc.html)

## T007｜Function Calling 也属于工具调用，请问什么场景下使用 Function Calling，什么场景下使用 MCP？

- 知识点：工具协议选型
- 前置知识：Function Calling、MCP
- 难度：中等
- 参考答案：如果工具少、只在单个应用内部使用，直接Function Calling加本地函数注册最简单；当工具需要跨应用复用、独立部署、动态发现或由第三方维护时，MCP可减少适配成本。两者并非互斥：MCP提供标准工具接入，模型仍可通过Function Calling表达选择。选型应看复用范围、部署边界和治理成本。例如，应用内部只有一个查天气函数，直接注册通常足够；多个产品都需要共享同一订单服务，可以用 MCP 统一暴露接口。但工具多并不自动意味着必须使用 MCP，还要评估鉴权、版本管理、传输故障和运维成本。采用 MCP 后模型选择工具的过程依然可以是 Function Calling。选择的核心是部署与复用边界，而不是 Agent 一定要 MCP、聊天应用只能 Function Calling。
- 评分要点：场景化选择，不把两者当替代关系。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/7_fc_vs_mcp_usage.html)

## T008｜为什么有些特定的推理模型不支持 MCP 协议？

- 知识点：MCP兼容性
- 前置知识：MCP
- 难度：进阶
- 参考答案：这道题需要先澄清前提：MCP 是 Host/Client 与 Server 之间的应用协议，不是直接写进模型权重的能力。所谓不支持，可能是宿主没有 MCP Client、模型接口暂未开放工具调用，或适配层没有正确处理工具消息与多轮执行。推理模型本身并不天然与 MCP 冲突，能否使用外部工具取决于具体接口、宿主和集成方式。排查时应依次确认：模型 API 是否支持工具定义与工具结果消息，适配层是否正确维护调用 ID 和多轮上下文，Host 是否兼容 Server 的协议版本与传输。推理过程的输出形式可能影响集成，但不是推理模型天生不能使用 MCP 的定律。即使模型缺少原生工具接口，也可以用结构化输出加受控解析适配，只是稳定性需要单独验证。判断结论应基于具体型号和调用链测试，而不是笼统归因于思维链无法中断。
- 评分要点：纠正模型原生支持 MCP 的前提；区分宿主协议实现、模型工具接口和适配问题；给出具体排查步骤。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/8_reasoning_no_mcp.html)

## T009｜Skill 是什么？

- 知识点：Agent Skill
- 难度：基础
- 参考答案：Agent Skill是把指令、脚本、模板和参考资料打包成可复用能力的机制，通常以包含SKILL.md及可选资源的目录存在。Agent可以发现Skill、按需加载说明，并在任务中使用其中的脚本和材料。它不是单纯保存Prompt，而是“操作手册+工具箱”；触发条件、步骤、输入输出、失败处理和安全边界都应写清楚。加载通常采用渐进方式：先用名称和描述判断是否相关，命中后读取完整步骤，再按需访问脚本、参考资料和模板，避免把全部资源永久放进上下文。例如，生成报告的 Skill 可以约定资料检查、内容组织、排版和验证流程。它提供的是任务方法，不会自动赋予工具权限；脚本执行仍受宿主的权限和环境约束。一个好的 Skill 需要明确适用范围与输入输出，避免对所有任务都触发。
- 评分要点：任务知识与流程封装，而非把Skill等同于API。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/9_skill.html)；[Agent Skills 格式规范](https://agentskills.io/specification)

## T010｜MCP 和 Agent Skill 的区别是什么？

- 知识点：工具协议选型
- 前置知识：MCP、Agent Skill
- 难度：中等
- 参考答案：MCP主要标准化外部能力如何被发现和调用，相当于工具连接层；Skill封装完成任务所需的方法、顺序和经验，相当于操作手册。一个Skill可以调用多个MCP工具，一个MCP工具也能被多个Skill复用。前者关注协议与能力，后者关注任务策略与可复用流程。例如，数据库 MCP 服务暴露查询能力，而数据分析 Skill 指导 Agent 先确认指标口径，再查询、检查异常并解释结果。Skill 可以使用本地脚本而不连接 MCP，MCP 也可以被没有 Skill 的程序使用，因此两者独立但互补。MCP 接口的质量主要看契约、兼容与可靠性，Skill 的质量更多看步骤是否合理和结果能否验证；使用二者都不能绕过运行时授权。
- 评分要点：工具连接层与任务知识层的区别和组合。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/10_mcp_vs_skill.html)

## T011｜Function Calling、Skill、MCP 这三个有什么区别？

- 知识点：工具协议选型
- 前置知识：Function Calling、MCP、Agent Skill
- 难度：中等
- 参考答案：Function Calling是模型输出结构化工具意图的机制；MCP是宿主连接、发现和调用外部能力的协议；Skill是指导Agent组合能力完成任务的知识与流程。可以理解为Function Calling提供调用语言，MCP提供标准化能力接口，Skill提供如何完成任务的方法，但具体实现中三者仍需权限、执行器和状态管理配合。以订单分析为例，Skill 给出核对时间范围、查询和总结的步骤；MCP 提供订单服务的工具描述与调用接口；Function Calling 让模型选择查询工具并填写参数。Host 将选择转成真实协议请求，得到结果后继续流程。三者分别处理任务方法、能力接入与模型意图，但都不是完整 Agent 控制器，仍需要外层管理状态、停止条件、执行结果和错误恢复。
- 评分要点：模型决策、能力接入、任务方法三个层次。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/11_fc_skill_mcp.html)

## T012｜什么是 A2A 协议？它和 MCP 协议的区别是什么？

- 知识点：A2A
- 难度：进阶
- 参考答案：A2A面向Agent之间的能力发现、任务委托、状态更新和结果交付，交互对象是相对自主的Agent；MCP面向Host与工具/资源服务的连接，调用对象通常是被动能力。A2A处理长任务协作、身份和任务生命周期，MCP处理工具调用和上下文接入，两者可以在同一多Agent系统中互补。例如，主 Agent 将一段研究任务交给外部研究 Agent，希望接收进度和最终报告，属于 Agent 协作；研究 Agent 自己调用搜索服务，可以使用 MCP。A2A 的任务可以经历进行中、等待补充输入、完成或失败等阶段，结果以产物交付，调用方不必了解对方内部提示或工具。能力发现不等于可信授权，跨组织协作还需要身份、超时、取消和产物验证，不能仅凭对方自称完成就接受结果。
- 评分要点：Agent协作与工具接入的对象、语义和生命周期差异。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/12_a2a_protocol.html)；[A2A 协议规范](https://a2a-protocol.org/latest/specification/)

## T013｜MCP 协议通常采用什么通信方式？

- 知识点：MCP传输
- 前置知识：MCP
- 难度：中等
- 参考答案：本地MCP Server常通过stdio由Client作为子进程启动，延迟低且无需开放端口；远程服务推荐使用Streamable HTTP，便于多Client共享和集中管理。早期HTTP+SSE双端点方案已不再是新项目的首选。无论使用哪种传输，消息层都采用JSON-RPC 2.0，传输方式只决定消息如何到达。stdio 使用标准输入输出传递协议消息，普通日志应写到 stderr，避免污染消息流。远程 Streamable HTTP 使用 HTTP 请求传递消息，并可通过 SSE 推送多个事件；并不是所有响应都必须保持一个长连接。2025-11-25 版规范列出这两种标准传输，旧 HTTP+SSE 应按兼容需求处理。客户端还要管理连接生命周期、会话和取消；重连不会自动保证外部操作只执行一次。
- 评分要点：区分 JSON-RPC 消息语义与传输；说明 stdio、Streamable HTTP 和旧 HTTP+SSE 的兼容关系。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/13_mcp_transport.html)；[MCP 2025-11-25 传输规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

## T014｜说说 WebSocket 和 SSE 通信的区别及局限性？

- 知识点：流式通信
- 难度：中等
- 参考答案：SSE基于HTTP长连接，主要由服务端向客户端单向推送文本事件，浏览器支持自动重连，适合LLM Token流；WebSocket升级为全双工连接，可双向低延迟传输文本或二进制，适合实时协作。SSE不适合高频双向和二进制媒体，WebSocket则需要自己处理心跳、重连、代理兼容和水平扩展。例如，文本生成可以用一次 HTTP 请求发送问题，再用 SSE 接收增量内容；用户取消可以另发请求，不必为所有对话引入 WebSocket。WebSocket 更适合双方持续发送事件，但可靠重连和消息去重仍由应用实现。SSE 的浏览器连接限制与 HTTP 版本有关，不能把 HTTP/1.1 的常见限制当作所有部署都相同。无论哪种方式，代理缓冲、心跳和慢消费者都会影响实际延迟。
- 评分要点：方向、协议、数据类型、重连与典型场景。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html)

## T015｜为什么要用 WebRTC 协议？它和 WebSocket 在 AI 对话流中的核心差异是什么？

- 知识点：实时通信
- 难度：进阶
- 参考答案：WebRTC针对实时音视频设计，包含媒体编解码、抖动缓冲、拥塞控制、NAT穿透和低延迟传输；WebSocket只是可靠的双向字节通道，这些媒体能力需自行实现。实时语音Agent通常用WebRTC承载音频和数据通道，用WebSocket传控制事件也可以，选择取决于延迟、媒体质量和部署复杂度。例如，用户语音输入与模型语音输出同时进行，还要支持打断和网络抖动，媒体通道更需要实时性而非等待每个旧包重新到达。WebSocket 常基于 TCP，丢包可能造成队头阻塞；WebRTC 有适合实时媒体的传输与带宽适应机制。不过 WebRTC 并不是绝对只走 UDP，也不是永远不重传，实际会受网络与中继影响。选择时比较通话质量、端到端延迟、穿透和运维，不应承诺固定毫秒数。
- 评分要点：媒体专用能力、传输特性及组合使用。

## T016｜有没有用过大模型的网关框架？网关层解决了什么问题？

- 知识点：模型网关
- 难度：进阶
- 参考答案：LLM网关在业务与模型供应商之间统一接口、鉴权、模型路由、限流、配额、重试、熔断、缓存、成本统计和观测，还可做敏感信息过滤。实践回答应说明具体框架或自研方案及路由策略。网关不应承担具体业务Prompt和Agent状态，否则会形成难维护的中心化逻辑。例如，一个团队同时接入多个模型供应商，网关统一记录费用、设置团队配额，并在可恢复故障时执行受控降级。但 SDK 统一调用和部署网关服务是不同层次的实现，回答时应讲清实际使用方式。缓存键应包含模型、参数、上下文和权限范围，不能把不同用户的私有回答混用。流式响应中途失败也不能简单重试后拼接重复内容，需要明确部分输出与恢复策略。
- 评分要点：横切能力完整；能说出实践和职责边界。

## T017｜工具很多时，Agent 如何做 Tool Routing，减少 Token 并避免选错工具？

- 知识点：工具路由
- 前置知识：Function Calling
- 难度：进阶
- 参考答案：先按领域和权限建立工具目录，为工具生成简洁、可区分的能力描述；运行时先做规则或语义检索得到小候选集，再让模型选择。可使用分层路由、工具组、历史成功率和上下文约束，并对高风险工具二次确认。评测应统计工具Recall、误选率、参数正确率、Token和延迟。例如，先按订单、文档和日程等领域筛选，再检索候选工具，最后只把少量相关 Schema 交给模型。第一阶段要保持足够召回，模型判断现有工具不合适时可以扩大候选范围，而不是被错误路由永久锁住。工具描述应包含何时使用、何时不用和参数语义；相似工具要有明确区分。权限过滤在执行时再次校验，路由正确不代表获得授权，评测还要覆盖容易混淆与无适用工具的请求。
- 评分要点：检索缩小候选、分层选择、安全控制和量化评测。

## T018｜工具调用格式非法、参数错误、超时或失败时，Agent 如何容错？

- 知识点：工具容错
- 前置知识：Function Calling
- 难度：进阶
- 参考答案：执行前用Schema校验并对可修复格式做受控纠正，缺少业务参数时向用户澄清；调用时设置超时、取消、幂等键和分类重试，失败后把结构化错误返回模型选择替代工具或降级。对部分成功的外部操作使用补偿事务，超过预算后停止并转人工，所有动作记录审计与Trace。需要区分明确失败和结果未知：例如请求超时后订单可能已经创建，此时优先用请求 ID 查询状态，再决定是否重试。幂等键应在第一次执行前生成并持久化，恢复时继续复用，不能每次重试换一个键。权限拒绝和业务参数错误通常不能原样重试，临时限流则可尊重 Retry-After 并做退避。补偿也是新的业务操作，可能再次失败，需要记录部分完成状态并准备人工接管。
- 评分要点：校验、澄清、超时重试、幂等、补偿和人工接管。
- 参考资料：[小林面试笔记题解](https://xiaolinnote.com/ai/tools/18_tool_reliability.html)
